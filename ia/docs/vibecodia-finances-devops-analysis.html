1. Sumário Executivo

O que o README original descreve como "aplicativo web para gerenciamento financeiro doméstico" é, na realidade, uma aplicação full-stack de produção ativa com múltiplos domínios, banco de dados multi-tenant via PIN, pipeline CI/CD orquestrada em repositório externo, PWA com push notifications, OCR de comprovantes via IA, sistema Kanban embutido e infraestrutura Nginx multi-vhost servindo pelo menos 6 aplicações distintas.

Esta análise cobre arquitetura, pipeline CI/CD, containers/Docker, Kubernetes (scaffold), segurança e gaps operacionais críticos.

3.1 Pontos Positivos da Pipeline

  • ✓ Semver automático baseado no tipo de branch (feature→minor, fix/hotfix/chore→patch, BREAKING CHANGE→major)
  • ✓ Detecção inteligente de mudança: separa app change de build/infra change
  • ✓ Verificação de conflito antes de qualquer build/deploy
  • ✓ Cleanup automático de imagens antigas no GHCR (mantém 3)
  • ✓ Polling com timeout para workflows externos (máx ~10 min)
  • ✓ AI-driven pipeline de tasks via GitHub Issues — design inovador

3.2 Gaps Críticos da Pipeline

CRÍTICO Sem testes automatizados — zero coverage

Os workflows executam npm run lint e npm run build, mas não há nenhum passo de teste (npm test). Não existe diretório __tests__, *.test.ts ou *.spec.ts no repositório. Qualquer lógica de negócio financeira pode regredir sem detecção.

CRÍTICO Poll de workflow externo é frágil — race condition

Em vibecodia-pipeline-call.yml, o job trigger-and-wait aguarda 15s após o dispatch e então consulta listWorkflowRuns per_page: 1. Se outro run do mesmo workflow foi criado por outro PR concorrente, o polling pode monitorar a execução errada e considerar o deploy concluído quando não foi.

ALTO Semver aplicado na branch de feature, não em develop/main

O bump de versão e o git push --tags ocorrem na branch do PR (github.head_ref), antes do merge. Se o PR for fechado sem merge, a tag fica órfã. Se dois PRs forem abertos simultaneamente, pode haver conflito de tag.

ALTO vibecodia-pipeline-call.yml dispara em PR edited

Qualquer edição no título ou corpo do PR dispara toda a pipeline — incluindo build de imagens e update de pods. Uma simples correção de typo no PR body pode gerar um deploy não intencional em produção.

4. Containers e Docker

4.1 Dockerfile.backend

CRÍTICO Stage 2 copia todo o contexto do projeto

A linha COPY . . no stage de produção inclui todo o código-fonte (frontend, infra, .github, ia/, etc.) na imagem final do backend — inflando a imagem desnecessariamente e expondo arquivos sensíveis. Deveria copiar apenas backend/.

ALTO Backend roda como root

Nenhum dos Dockerfiles define um usuário não-privilegiado (USER node). O processo Node roda como root dentro do container, o que amplia a superfície de ataque em caso de vulnerabilidade RCE.

MÉDIO Frontend usa npm install em vez de npm ci

O Dockerfile.frontend usa RUN npm install no stage de build. Deveria usar npm ci para garantir builds determinísticos e evitar instalação de versões diferentes do package-lock.json.

MÉDIO docker-compose.yml dev usa target incorreto

O compose de desenvolvimento usa target: build no stage do frontend mas roda npm run dev, enquanto o Dockerfile foi projetado para Nginx em produção. O dev mode funciona por acidente via volume mount, não por design correto.

4.2 Nginx (multi-vhost)

ALTO nginx.conf gerencia 6 aplicações distintas em um único arquivo

O arquivo inclui vhosts para vibecodia.com.br, finances.vibecodia.com.br, atelie.vibecodia.com.br, webids.vibecodia.com.br, playground.vibecodia.com.br e api.vibecodia.com.br. Isso significa que uma única imagem frontend é ponto único de falha para todos esses serviços. Qualquer erro de configuração pode derrubar tudo.

MÉDIO Sem rate limiting no Nginx para /api/

O Nginx não tem diretivas limit_req_zone nem limit_conn_zone. Os endpoints da API — incluindo /api/verify-pin — estão expostos a força-bruta sem throttling.

POSITIVO TLS bem configurado

TLSv1.2/1.3 com cipher suite moderna, HSTS implícito via redirect HTTP→HTTPS e suporte a ACME challenge para renovação automática de Let's Encrypt. Configuração sólida.

5. Kubernetes — Scaffold Kustomize

O scaffold K8s está bem estruturado mas é apenas ponto de partida. Vários gaps precisam ser resolvidos antes de poder ser aplicado em produção.

ComponenteEstadoGap Identificado
Backend Deployment Parcial Probes usam tcpSocket em vez de HTTP GET no /api/health-check. Não valida se a aplicação responde, apenas se a porta está aberta.
Frontend Manifests Ausente base/frontend/kustomization.yaml tem resources: []. Não existe Deployment nem Service para o frontend. O cluster K8s não consegue servir o frontend.
Secret Placeholder secret.yaml contém valores placeholder em texto claro no repositório. Precisa de solução como Sealed Secrets, External Secrets Operator ou Vault.
Ingress Parcial Aponta para vibecodia.local. Não há patch de overlay para produção com o domínio real. cert-manager está scaffoldado mas sem ClusterIssuer real.
Overlays dev/prod Vazio Ambos os overlays herdam apenas a base sem nenhum patch. Prod roda com NODE_ENV: development (do configmap base).
HPA / PDB Ausente Sem HorizontalPodAutoscaler nem PodDisruptionBudget. Sem estratégia de deploy (RollingUpdate está no default implícito, mas não explicitado).
Resource Limits Presente Backend tem requests/limits definidos (100m/500m CPU, 128Mi/512Mi RAM). Boa prática mantida.

6. Segurança

CRÍTICO Autenticação via PIN: sem rate-limit, sem lockout, sem MFA

O endpoint POST /api/verify-pin apenas verifica se o PIN existe em DB_CONN_MAP. Não há: rate limiting, bloqueio após tentativas falhas, expiração de sessão no servidor, ou rotação de PIN. Um atacante pode fazer força-bruta ilimitada.

CRÍTICO app.use(cors()) sem restrição de origem

O CORS está configurado como cors() sem opções, o que permite qualquer origem (Access-Control-Allow-Origin: *). Qualquer site malicioso pode fazer chamadas autenticadas à API se o usuário tiver um cookie válido.

ALTO Segredo de banco multi-tenant em variável de ambiente única

MONGO_CONN_MAP é um JSON com todas as connection strings de todos os tenants (usuários) em uma única variável. Um vazamento dessa variável expõe todos os bancos de todos os usuários simultaneamente.

ALTO PIN passado em header/query não criptografado

O middleware dbMiddleware aceita o PIN via x-pin header ou ?pin= query string. Passar credenciais em query string as coloca em logs de servidor, histórico de browser e intermediários.

ALTO MY_PAT com escopo amplo usado em múltiplos workflows

O mesmo Personal Access Token (MY_PAT) é usado para: push de tags, criação de PRs, dispatch de workflows em repositório externo (vibecodia-pipelines), release no GitHub, login no GHCR. Não há separação de privilégios. Um vazamento compromete toda a pipeline.

MÉDIO source maps: true habilitado em produção

O vite.config.ts tem sourcemap: true para todos os builds. Source maps são excelentes para debug mas expõem o código-fonte original aos usuários finais em produção.

MÉDIO Sem Content Security Policy (CSP) no Nginx

Nenhum header de segurança HTTP está configurado: sem Content-Security-Policy, sem X-Frame-Options, sem X-Content-Type-Options, sem Referrer-Policy. A aplicação está vulnerável a XSS, clickjacking e MIME-sniffing.

7. Gaps Operacionais

GapSeveridadeImpacto
Sem estratégia de backup do MongoDB CRÍTICO Dados financeiros sem backup automatizado. O script export_import.sh é manual e copia apenas a coleção transactions.
Sem observabilidade (logs estruturados, métricas, tracing) ALTO Nenhum APM, nenhum log aggregator (ELK/Loki), nenhuma métrica de negócio. Falhas silenciosas nos cron jobs não são alertadas.
Sem ambiente de staging dedicado ALTO A pipeline vai de feature/* direto para produção após merge. Não há validação em ambiente idêntico ao prod.
Cron jobs acoplados no servidor Express MÉDIO Se o servidor reiniciar às 09h, o lembrete do dia é perdido. Cron jobs deveriam ser um worker separado ou usar CronJob do K8s.
Sem strategy de rollback documentada MÉDIO Imagens são mantidas (3 versões no GHCR), mas não há kubectl rollout undo ou equivalente Docker documentado.
README desatualizado e incompleto BAIXO O README descreve a estrutura original de src/ (monorepo flat), mas o projeto usa frontend/src/. Onboarding de novos devs é prejudicado.

8. Pontos Positivos e Boas Práticas

  • ✓ Multi-stage Docker builds — imagem de build separada da de produção para ambos os serviços.
  • ✓ Healthcheck no Docker Compose prod — backend tem healthcheck funcional com depends_on: condition: service_healthy.
  • ✓ Semver totalmente automatizado — eliminação de versioning manual com bumps baseados em convenção de branch.
  • ✓ Kustomize com overlays — separação correta de base e overlays, mesmo que os overlays ainda estejam vazios.
  • ✓ Gerenciamento de conexões multi-tenant — o padrão de ConnectionManager com cache por PIN é elegante e evita reconexões desnecessárias.
  • ✓ Timezone explícito — TZ=America/Sao_Paulo definido nos containers e nos cron jobs, evitando erros sutis de horário.
  • ✓ AI-driven tasks via Issues — pipeline inovadora de 790 linhas que usa IA como co-desenvolvedor via GitHub Issues.
  • ✓ Limpeza automática de imagens GHCR — evita acúmulo ilimitado de artefatos no registry.

10. Conclusão

O vibecodia-finances é uma aplicação de produção ativa com nível de complexidade significativamente maior do que sua documentação indica. A pipeline CI/CD tem design sofisticado e demonstra maturidade em automação. Contudo, a ausência de testes, os gaps de segurança na autenticação e na configuração CORS, e a imaturidade da infraestrutura K8s (overlays vazios, frontend sem manifests, secret com placeholders em texto claro) representam riscos reais para um sistema que lida com dados financeiros pessoais.

A base é sólida. Com as remediações de CRÍTICO e ALTO aplicadas, a aplicação atinge um nível adequado de maturidade DevOps para produção.
